# CalculatorX 开发者协作指南

本文档说明参与 CalculatorX 开发时应遵循的协作流程。代码写法见 [代码风格指南](./code-style.md)，系统设计与模块边界见 [架构文档](./architecture.md)。

## 1. 开发前

修改代码前，先确认改动所属模块及影响范围。

- 系统整体设计、模块边界：阅读 [架构文档](./architecture.md)。
- UI、计算器模块、键盘与主壳：阅读 [模块与 UI](./architecture/modules-and-ui.md)。
- EventHub、AppStorage、Preferences、RDB：阅读 [状态与持久化](./architecture/state-and-storage.md)。
- 具体子系统存在专题文档时，优先阅读对应文档。

不要仅为方便调用而绕过已有架构边界，也不要在一次功能修改中顺手重构无关代码。

## 2. 实现要求

所有新增代码和被实质修改的代码必须遵守 [代码风格指南](./code-style.md)。

开发时遵循以下原则：

- 一次改动只处理一个明确主题。
- 优先复用现有组件、服务和协议，不创建职责重复的实现。
- 修改公共接口、状态契约、协议字段或持久化结构时，同步检查所有生产者、消费者、测试和相关文档。
- 不提交密钥、令牌、签名材料、真实服务凭据、本机私有路径或其他敏感信息。
- 不提交临时调试代码、无关格式化或生成产物，除非这些文件本身就是提交目标。
- 修复缺陷时，应尽可能在最接近根因的测试层增加回归覆盖。

如果改动改变了系统架构、模块职责、核心调用链、状态协议或持久化方式，应同步更新对应的 `docs/architecture/` 文档。

## 3. 验证

验证范围应与改动风险匹配，不需要为所有修改无条件执行完整构建。

提交前至少：

1. 检查 `git diff`，确认没有无关改动、调试输出或敏感信息。
2. 运行：

   ```bash
   git diff --check
   ```

3. 对修改过的代码执行适用的 lint、静态检查或相关测试。
4. 功能或缺陷修复应执行能够覆盖本次行为的最小有效测试集。

以下情况通常需要进一步执行构建或集成验证：

- 构建配置或依赖发生变化；
- 公共 API、N-API、路由或资源引用发生变化；
- 修改可能影响 HAP 构建结果；
- 无法通过局部检查确认正确性；
- PR 或任务明确要求完整构建。

验证记录必须反映实际执行结果。没有运行的构建、设备测试或兼容性测试不得写成“已通过”。

## 4. Commit 规范

Commit Message 使用以下前缀：

| 前缀 | 用途 |
| --- | --- |
| `feat:` | 新增功能 |
| `fix:` | 修复缺陷 |
| `refactor:` | 不改变外部行为的重构 |
| `perf:` | 性能优化 |
| `style:` | 不影响逻辑的样式或格式调整 |
| `test:` | 测试相关修改 |
| `docs:` | 文档修改 |
| `build:` | 构建系统或依赖修改 |
| `ci:` | CI 配置修改 |
| `chore:` | 其他维护工作 |

标题应直接说明结果，例如：

```text
feat: 增加程序员模式位编辑
fix: 修复历史记录恢复有符号状态
refactor: 拆分程序员输入会话
```

一个 Commit 应保持主题清晰，避免混入无关修改。

## 5. 分支变更说明

新增功能、用户可见修复以及影响数据、配置、兼容性或模块行为的分支，在合并前应按照 [分支变更说明规范](./changes/README.md) 在 `docs/changes/` 中记录最终结果。

变更说明用于保存：

- 用户可见行为；
- 关键实现边界；
- 兼容性和已知限制；
- 实际验证结果；
- Release / CHANGELOG 可复用的摘要。

纯文档、拼写修正和不影响行为的小型内部整理通常不需要单独建立变更说明。

## 6. Pull Request

提交 PR 前确认：

- 改动范围与分支目标一致；
- 新增和修改代码符合 [代码风格指南](./code-style.md)；
- 没有无关格式化、临时日志、废弃代码或敏感信息；
- 相关测试和检查已经执行；
- 架构或协议发生变化时，相关文档已经同步；
- 需要变更说明的分支已经更新 `docs/changes/`。

PR 描述应说明：

- 修改了什么；
- 为什么需要修改；
- 如何验证；
- 尚未验证或存在的限制。
