# 分支变更说明

本目录保存已经完成、准备合并的功能与修复说明。每个分支维护一份独立文档，在实现和验证完成后、合并前更新为最终内容。

这套记录用于保留一次变更的完整上下文，也是后续编写 `docs/CHANGELOG.md` 和 GitHub Release 的素材来源。Changelog 只保留按版本整理的用户向摘要，具体设计和验证信息保留在本目录中。

## 何时需要编写

以下分支在合并前应新增变更说明：

- 新增或改变用户可见功能；
- 修复影响用户使用的问题；
- 改变数据、兼容性、配置或模块间行为；
- 需要在发布说明中告知用户或维护者的其他变更。

纯文档修改、拼写修正以及不影响行为的内部整理通常不需要单独创建。如果一个分支包含彼此独立的多项功能或修复，应拆分文档，避免将无关内容写在一起。

## 文件命名

文件名使用完成日期和简短主题：

```text
YYYY-MM-DD-topic-slug.md
```

例如：

```text
2026-09-15-result-ready-input-flow.md
```

主题应与分支目标一致，并使用稳定、可搜索的英文短语。如果同一天出现重名主题，可补充模块名区分。

## 推荐结构

每份说明应记录已经实现的最终结果，而不是开发过程或尚未执行的计划。根据变更规模删减不适用的章节，但至少保留摘要、行为变化和验证信息。

```markdown
# 变更标题

- 状态：已完成
- 类型：功能 / 修复 / 重构
- 分支：`feature/example`
- 关联：Issue 或 PR 链接
- 完成日期：YYYY-MM-DD

## 变更摘要

说明解决了什么问题，以及用户现在会看到什么结果。

## 用户可见行为

列出主要操作及其结果。

## 设计与实现

说明关键状态、数据职责或兼容处理，帮助后续维护者理解实现边界。

## 兼容性与边界

说明适用模块、明确排除项和已知限制。

## 验证

记录实际完成的人工验证和静态检查，并明确未执行的验证。

## 主要文件

列出承担本次行为的主要源码或配置文件。

## 发布说明素材

提供一段可直接整理进 Tag 或 Release 的用户向说明。
```

不要把计划中的预期行为写成已经完成，也不要声称未执行的构建、设备或兼容性验证已经通过。文档中的路径、模块名、Issue 和行为应以当前分支为准。

## 发布时汇总

发布新 Tag 前，用上一个 Tag 与待发布提交之间新增的变更说明作为候选清单：

```powershell
git diff --name-only --diff-filter=A <previous-tag>..HEAD -- 'docs/changes/*.md' ':(exclude)docs/changes/README.md'
```

逐份提取“发布说明素材”，按功能、修复等类别整理成版本摘要，并在 [`docs/CHANGELOG.md`](../CHANGELOG.md) 的现有版本记录上方新增当前版本。相同摘要可用于 GitHub Release。

从 `v1.6.4` 开始，版本标题统一使用实际 Tag 名称和发布日期，例如：

```markdown
## [v1.6.4] - 2026-09-XX
```

Changelog 中的重要功能或修复可以在条目末尾附上对应的分支变更说明，方便读者查看完整行为、实现边界和验证信息。链接文字使用便于识别的文档名，可以省略文件名中的日期前缀。不要求每一条都添加链接，应优先链接需要进一步说明或具有代表性的变更。例如：

```markdown
- 优化计算完成后的连续输入，并修复结果接续百分号的解析问题。（[result-ready-input-flow.md](./changes/2026-09-15-result-ready-input-flow.md)）
```

Changelog 不需要复制各分支说明的实现细节，也不需要重新倒查提交。目录 README 不登记每一份说明，因此新增分支文档时无需同步维护索引。
