## 我对 CalculatorX 的总体评价

截至 **2026 年 9 月 18 日主分支**，如果把它当成一个个人/小团队开源项目看，我认为它的工程化程度明显高于常见同规模项目。它最突出的优点不是“代码格式特别整齐”，而是已经建立了一套相当完整的**架构知识体系和工程约定**。

但它目前存在一个很明显的阶段性特征：

> **“规范体系已经比较成熟，但自动化执行体系还没有完全追上规范体系。”**

也就是说，现在更像是**文档驱动 + 开发者自觉 + 手工验证**，还没有完全进化成**CI 门禁驱动**的工程体系。

我会这样分项评价：

### 文档是这个项目目前最明显的长板

我认为 CalculatorX 的文档不能只评价为“多”，而应该评价为**已经开始形成知识架构**。

比如架构文档没有停留在：

> `components` 是组件，`utils` 是工具。

而是会解释 MathJSON 为什么作为 IR、为什么同时使用 SymEngine/Giac、WebView 怎样参与计算、数据如何从 ArkTS 穿过 N-API 进入 C++。([GitHub][3])

尤其是 Windows 语义自动化那份文档，我认为是比较有价值的工程设计。HarmonyOS 项目的自动化环境不像普通 Node 项目那么方便，项目没有简单假装“所有东西都能 GitHub Actions 一键跑”，而是设计 `engine / setup / ui` 三条实际测试路径，并强调稳定语义 ID，而不是脆弱的屏幕坐标点击。([GitHub][6])

最新 API 26 分支的 change document 也值得肯定：它不只是说“升级 API 26”，还记录了兼容边界、采用什么实现方案、哪些 build 已经通过，以及 **API 23 / 部分真机验证仍未完成**。主动记录“没验证什么”是很好的工程习惯。([GitHub][8])

问题恰恰也是因为文档越来越多：**维护成本开始出现了。**

README 的 SDK 要求、project structure、CHANGELOG 和实际代码之间已经有轻微漂移。这不说明“文档差”，反而说明这个项目正在从“写文档”进入下一个阶段——需要解决**如何让文档不腐化**。

## 关于“历史遗留”，我会这样划线

以后如果审这个项目，我会把代码分成三类：

**第一类：规范形成之前的代码。**
诸如早期 `EngineService.ets`，除非存在 bug、安全问题或者本来就在重构范围里，否则**不应该因为今天的文件头规范、格式规范而扣分**。项目自己的治理原则也支持这种做法。([GitHub][1])

**第二类：旧文件后来做了实质修改。**
这类要看修改范围。比如函数被重写了，那么相关部分最好逐渐向新规范靠拢；但不应该因为只修一行 bug，就顺手格式化整个 500 行文件，制造巨大的 diff。

**第三类：规范体系已经存在时新增的文件。**
这才是真正检验执行力的对象。

所以 `ImmersiveMaterialUtils.ets` 比 `EngineService.ets` 更值得关注。它本身代码并没有明显问题，甚至职责相当单一——集中处理 API 26 的材质兼容；真正的问题只是：

```text
@file 1.ets
@description 请在此处输入文件描述...
@date 2026/9/18 13:55
```

与当前规范要求的真实文件名、有效描述和 `YYYY-MM-DD HH:mm` 不一致。([GitHub][5])

不过这里还有一个重要的时间因素：它和代码规范的完善都发生在同一个 API 26 开发周期，所以仅凭最终 Git 状态，我不会下结论说“开发者已经有规范却不遵守”。更准确的评价是：

> **规范已经进入仓库，但缺乏自动验证，所以最终合并状态仍存在规范与实现不完全一致。**

这也是为什么我认为 CI 是目前最大的提升点。

## 如果我是这个项目的维护者，我会优先做什么

我不会优先去“清洗所有老代码”，那样投入产出比很低。优先级我会排成：

1. **先建设一个轻量 PR Quality Gate。** 最基础可以只有 `git diff --check`、ArkTS lint、文件头检查、PowerShell 静态检查、文档链接/关键配置一致性检查；HarmonyOS 完整编译如果 GitHub Hosted Runner 环境困难，可以放到自托管 runner，真机测试继续作为手工或定时任务。这样能立刻解决“规范写了但没人保证执行”的核心问题。([GitHub][1])
2. **补 PR template + commit lint。** PR 至少要求填写“做了什么 / 为什么 / 如何验证 / 未验证什么 / 是否影响兼容性”。项目的 branch change document 已经有很好的模板，可以直接复用其思想。Commit 方面允许 `feat/fix/refactor/docs/style/perf/chore/test/build/ci` 等，再用 commitlint 防止 `docs：` 这种无意的不一致。
3. **把 CHANGELOG → Release 做成闭环。** 现在已经有 `docs/changes/YYYY-MM-DD-xxx.md` 这套很好的原材料，发布时完全可以半自动聚合成 CHANGELOG 和 Release Notes，避免文档写了两套却不同步。([GitHub][13])
4. **解决文档漂移，而不是继续增加文档。** 例如 Target SDK 最好只在一个机器可读位置定义，其余文档引用/生成；项目结构文档则可以加脚本检查关键路径是否实际存在。
5. **补安全治理的“外壳”。** 加 `SECURITY.md`、依赖更新策略、第三方许可证清单；如果 C++ 第三方包继续 vendoring，至少定期扫描版本与 CVE。
6. **最后才是渐进整改老代码。** 谁碰到旧模块，谁在合理范围内顺手改善；没有业务理由就不要为了“100% 风格统一”制造巨大 diff。这与项目当前自己提出的渐进式规范化原则是一致的。([GitHub][1])

### 一个我认为很关键的判断

如果只看代码格式，我可能会给这个仓库一个普通的“B”。

但如果把**架构设计、计算链路文档、测试思路、变更文档、目录职责、版本发布**都算进去，它明显不是一个“随手写出来能跑就行”的项目。

我会把它当前阶段概括成：

**工程设计成熟度 > 工程自动化成熟度。**

它已经比较清楚地知道：

* 代码应该怎么写；
* 模块为什么这么分；
* 变更应该记录什么；
* 测试应该验证什么；
* 历史代码应该怎么渐进治理。

现在欠缺的是让机器回答：

> “这些规则这次提交到底有没有做到？”

所以如果按**个人开源项目**的标准，我会认为整体大约在 **8/10 左右，属于工程化相当不错的一档**；如果拿去和有多人协作、branch protection、强制 review、完整 CI/CD、安全扫描的大型生产仓库相比，则大约是 **7/10 左右**。差距主要不是代码本身，而是**自动化门禁、协作治理和发布闭环**。
