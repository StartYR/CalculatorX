# CalculatorX 代码风格指南

本文档规定 CalculatorX 新增代码以及被实质修改代码的默认写法，适用于 ArkTS/ArkUI、C++/N-API、PowerShell 和项目维护的 JSON/JSON5 文件。

模块职责、状态边界和系统设计不在本文档重复规定，相关要求以 [架构文档](./architecture.md) 及 `docs/architecture/` 下的专题文档为准。

第三方源码、压缩资源、生成文件和构建产物不适用本文档的格式化规则。

若本文档与编译器、DevEco Studio、`code-linter.json5`、`.clang-tidy` 或更具体的项目规则冲突，以可执行配置和更具体的规则为准。

## 1. 通用原则

- 优先保证代码正确、清晰和可维护，不用复杂抽象替代简单实现。
- 一次修改只处理当前任务，不顺手格式化、改名或重构无关代码。
- 外部输入在进入计算、持久化、网络或 N-API 边界前必须校验。
- 错误路径必须有明确的返回、异常或日志策略。
- 标识符使用英文；注释和开发者可见说明使用简洁中文，通用技术名词保留英文。
- 文件使用 UTF-8，并保留文件末尾换行。
- 禁止行尾空格，不使用空格进行视觉对齐。
- 一行原则上不超过 120 个字符；正则、LaTeX、协议文本和不宜拆分的 ArkUI 属性可例外。
- 优先使用清晰命名表达“做什么”，注释负责说明“为什么”和必须维持的约束。
- 不在源码、注释、日志或示例中写入真实密钥、密码、令牌和签名材料。

## 2. 文件与命名

### 2.1 文件命名

- ArkTS 组件、页面、类和主要类型：`PascalCase.ets`
- C++ 类和主要模块：`PascalCase.h/.cpp`
- 已有底层 C++ 文件沿用所在目录现有命名方式
- PowerShell 命令脚本：`Verb-CalcXSubject.ps1`
- PowerShell 共享模块：`PascalCase.psm1`
- 测试文件沿用框架后缀，如 `Programmer.test.ets`
- 场景和测试数据使用小写 kebab-case，如 `programmer-ui-smoke.json`

不要创建与现有目录或模块职责重复的新层级。

### 2.2 标识符

| 对象 | 风格 | 示例 |
| --- | --- | --- |
| 类、接口、结构体、类型、ArkUI 组件 | `PascalCase` | `EngineService` |
| 函数、方法、字段、局部变量、参数 | `lowerCamelCase` | `requestId` |
| 模块级常量、协议常量、枚举成员 | `UPPER_SNAKE_CASE` | `MAX_BATCH_ITEMS` |
| PowerShell 函数 | `ApprovedVerb-CalcXNoun` | `Invoke-CalcXProcess` |
| PowerShell 参数 | `PascalCase` | `$TimeoutSeconds` |
| PowerShell 局部变量 | `lowerCamelCase` | `$resolvedPath` |

补充要求：

- 布尔值优先使用 `is`、`has`、`can`、`should` 等前缀。
- 回调使用 `onXxx`。
- 主动执行动作的方法以动词开头。
- 单位体现在名称中，如 `durationMs`、`timeoutSeconds`。
- 避免无意义缩写和单字母名称；数学变量和短循环索引除外。
- 外部协议字段可以保留其原始命名，映射后的内部代码仍使用项目命名风格。

## 3. 文件头与注释

### 3.1 新文件头

新建 `.ets`、`.cpp`、`.c`、`.h` 文件时必须使用完整文件头：

```text
/**
 * Copyright (c) YYYY StartYi. All rights reserved.
 * @file FileName.ext
 * @description 用一句话说明文件当前职责
 * @author StartYi
 * @date YYYY/MM/DD HH:mm
 */
```

要求：

- `@description` 描述文件当前职责，不记录开发过程。
- `@author` 和 `@date` 不得省略。
- `@date` 为文件创建时间，普通修改不更新。
- 既有文件头只有在本次修改涉及头部或内容明显错误时才修正。
- 第三方、生成文件不添加项目文件头。

### 3.2 必须写注释的情况

以下代码不能仅以“代码本身可读”为理由省略说明：

- 非直观算法、数学推导和数据结构；
- 位运算、编码/解码、IEEE 754、舍入、溢出、截断和符号扩展；
- 特殊边界值或异常输入处理；
- 协议、存储格式、单位或状态不变量；
- 为性能、兼容性、平台限制或第三方行为采取的特殊实现；
- 看似可以删除或简化，但实际上必须保留的逻辑；
- 存在非显然前置条件、返回语义、副作用或错误行为的公共接口。

注释应解释：

- 为什么这样实现；
- 有什么边界或约束；
- 修改时必须保持什么行为。

### 3.3 注释形式

- 简短说明使用 `//`。
- 非直观算法、公共数据契约和复杂接口使用 `/** ... */`。
- ArkTS 文档注释按需要使用 `@param`、`@returns`、`@throws`。
- C++ 公共接口在头文件中使用 `@brief`、`@param`、`@return`。
- 注释紧邻对应代码，并随实现同步更新。
- 长函数可以用简短的小节注释划分阶段。

禁止：

- 逐句翻译代码，例如“给变量加一”；
- 描述协作过程，例如“新增逻辑”“按要求修改”；
- “终极方案”“绝对安全”等无依据表述；
- 长期保留被注释掉的旧实现；
- 与当前实现不一致的过期注释。

`TODO` 必须说明具体未完成事项并尽量关联可追踪依据：

```text
TODO(#123): 补充 API 23 兼容路径
```

## 4. ArkTS 与 ArkUI

### 4.1 基本格式

- 使用 2 个空格缩进，不使用 Tab。
- 语句以分号结束。
- 字符串默认使用单引号；需要插值时使用模板字符串。
- 左花括号与声明或控制语句同行。
- `else`、`catch` 与前一个右花括号同行。
- 默认使用 `const`，需要重新赋值时才使用 `let`，禁止 `var`。
- 导出函数、公共方法、异步边界和回调显式写出参数与返回类型。
- 不使用 `any` 绕过类型系统。
- 复杂协议对象和跨组件数据使用具名 `interface` 或 `type`。

### 4.2 Import

按以下顺序分组：

1. HarmonyOS / Kit
2. 第三方依赖
3. 项目内相对模块

组间空一行，组内保持稳定顺序。

### 4.3 ArkUI

- `@Component`、`@Entry` 等装饰器紧邻声明。
- 状态字段、普通字段、回调、辅助方法和 `build()` 按稳定顺序排列。
- ArkUI 属性链原则上一行一个调用。
- 同一组件的属性顺序保持稳定：布局 → 语义/无障碍 → 视觉 → 动画 → 事件。
- 重复的视觉值、按键映射和语义 ID 应抽取为常量或共享配置。
- 需要自动化或无障碍定位的交互控件使用稳定语义 ID，并提供准确的 `accessibilityText`。
- 主题颜色优先使用系统或应用资源，不跨组件复制硬编码色值。
- 较长事件处理器提取为具名方法；行内 lambda 只承担简单转发或单一状态更新。

状态所有权和 AppStorage/EventHub 的使用边界见 [状态与持久化](./architecture/state-and-storage.md)。

### 4.4 类型与异步

- JSON、N-API、网络和持久化数据在访问字段前完成类型收窄或结构校验。
- `catch` 中不要假定未知错误一定存在 `message`。
- 异步函数返回明确的 `Promise<T>`。
- 调用方必须明确 `await`、返回 Promise 或有意执行 fire-and-forget。
- 需要释放的 ResultSet、计时器、订阅和其他资源必须覆盖所有退出路径，必要时使用 `finally`。
- 用户可见且需要本地化的文本进入资源文件。

## 5. C++ 与 N-API

### 5.1 格式

- 使用 4 个空格缩进，不使用 Tab。
- 使用同行左花括号。
- 头文件优先使用 `#pragma once`。
- 不在头文件中使用 `using namespace`。
- include 顺序：

    1. 对应头文件
    2. C/C++ 标准库
    3. 第三方库
    4. 项目头文件

  分组之间空一行。

- 类、结构体、枚举使用 `PascalCase`。
- 函数、方法和局部变量使用 `lowerCamelCase`。
- 编译期常量和枚举成员使用 `UPPER_SNAKE_CASE`。
- 不依赖隐式窄化转换。

### 5.2 边界与资源

- N-API 入口先验证参数数量、类型及每一步 API 返回值。
- ArkTS 传入的模式值、精度、数组和字符串长度必须有明确边界。
- 优先使用 RAII、标准容器和智能指针。
- 避免裸 `new` / `delete` 和不明确的所有权传递。
- 不吞掉未知异常并伪造成功结果。
- 热路径缓存和静态状态必须说明键、生命周期或线程假设。
- 日志使用项目现有 `LOG*` 接口，不输出凭据或无边界的大型输入。

## 6. PowerShell

- 脚本入口使用 `[CmdletBinding()]`。
- 参数块位于文件顶部。
- 使用 4 个空格缩进。
- 入口脚本启用：

  ```powershell
  Set-StrictMode -Version 3.0
  $ErrorActionPreference = 'Stop'
  ```

- 函数使用 `Verb-Noun`，项目函数以 `CalcX` 限定命名。
- 参数使用具体类型声明。
- 默认使用单引号，需要变量插值时使用双引号。
- 文件路径使用 `Join-Path`、`Resolve-Path -LiteralPath`、`Test-Path -LiteralPath` 等安全接口。
- 调用外部进程时显式处理退出码、stdout、stderr 和超时。
- 供其他工具消费的标准输出保持机器可读，诊断信息不要混入协议输出。
- 临时资源必须在 `finally` 中清理。

## 7. JSON 与 JSON5

- 使用 2 个空格缩进。
- 字段按照协议或业务阅读顺序稳定排列。
- `.json` 不使用注释和尾逗号。
- 只有 `.json5` 可以使用 JSON5 语法。
- 协议字段、模式值和语义 ID 视为兼容性接口。
- 修改兼容性接口时同步更新生产者、消费者、测试和文档。
- 测试数据名称应描述行为，不使用 `test1`、`temp` 等临时命名。
- 模板只包含占位值，不包含真实凭据或本机私有路径。

## 8. 日志、错误与测试

### 日志

- ArkTS 使用项目 `Logger`。
- C++ 使用项目 `LOG*` 接口。
- 不在业务代码中保留临时 `console` 输出。
- 日志说明阶段、对象和结果，不使用“到这里了”“看看值”等临时措辞。
- 高频路径谨慎使用 `info`。
- 不记录密钥、完整隐私数据或无边界的大型表达式。

### 错误

错误信息应明确：

- 什么操作失败；
- 哪个对象或输入存在问题；
- 调用方下一步可以做什么。

不得向最终用户直接暴露秘密或不适合展示的底层异常。

### 测试

- 测试名称描述行为和预期结果。
- 单个测试聚焦一个行为。
- 准备、执行、断言阶段应清晰。
- 回归测试放在最接近根因的测试层。
- UI 自动化优先使用稳定语义 ID，不依赖屏幕坐标、动画时序或易变文案。
- 测试场景必须可重复，不依赖未声明的本地状态。

## 9. 检查

提交源码修改前至少完成：

1. 查看 `git diff`。
2. 运行：

   ```bash
   git diff --check
   ```

3. ArkTS 改动执行 `code-linter.json5` 对应检查。
4. C++ 改动检查编译器、clangd 和 `.clang-tidy` 相关诊断。
5. PowerShell、协议和测试数据执行相应语法检查或最小自测试。
6. 功能修改运行能够覆盖当前行为的相关测试。

构建和更大范围验证按改动风险决定，具体协作要求见 [开发者协作指南](./CONTRIBUTING.md)。

## 10. 例外

确实需要违反本文档时：

- 例外范围必须尽可能小；
- 不得通过关闭整类 lint 或静态检查规则掩盖单点问题；
- 非显然原因应在代码注释或变更说明中记录。

不要仅为了让旧代码符合本指南而批量改写与当前任务无关的文件。
