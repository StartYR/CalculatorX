# CalculatorX 代码风格指南

本文档规定 CalculatorX 新增代码以及被实质修改代码的默认风格，适用于 ArkTS/ArkUI、C++/N-API、PowerShell 和项目维护的 JSON/JSON5 文件。

项目已有代码包含不同时期形成的写法。提交功能或修复时，应让本次新增和修改的代码符合本文档，但不得仅为统一风格而批量改写无关文件。第三方源码、压缩资源、二进制库、生成文件和构建产物不在本文档的格式化范围内。

若本文档与编译器、DevEco Studio、[`code-linter.json5`](../code-linter.json5) 或更具体的项目规则冲突，以可执行配置和更具体的规则为准。

## 1. 通用原则

- 一次提交只处理一个清晰主题，不顺手格式化、改名或重构无关代码。
- 优先保持代码可读和边界清楚，不用复杂抽象替代简单、稳定的实现。
- 对外部输入先校验，再进入计算、持久化或 N-API 边界；错误分支必须有明确的返回、异常或日志策略。
- 密钥、密码、令牌、签名材料和真实服务凭据不得写入源码、注释、日志或示例。敏感配置只保留无真实值的模板。
- 代码标识符使用英文；注释和开发者可见的说明使用简洁中文，API、LaTeX、MathJSON、N-API、RPN 等通用技术名词保留英文。
- 文件使用 UTF-8 并保留文件末尾换行；编辑既有文件时保持其换行符，不制造整文件换行差异；禁止行尾空格。
- 一行尽量不超过 120 个字符。正则表达式、LaTeX、ArkUI 属性链和无法合理拆分的协议文本可以例外，但应优先按语义换行。
- 使用空行分隔逻辑阶段，不连续堆叠多个空行；不要用空格做垂直对齐，以免后续修改产生无意义差异。

## 2. 目录与职责

代码应放入最接近其职责的目录，不以“调用方便”为理由跨层堆放：

- `entry/src/main/ets/pages/`：页面级容器、导航和模块装配，不承载具体计算器业务实现。
- `entry/src/main/ets/components/`：可组合的业务组件与 UI；子领域代码进入对应子目录，如 `graphing/`、`exchange/`。
- `entry/src/main/ets/utils/`：无 UI 的通用逻辑、平台能力封装和 N-API 调度。
- `entry/src/main/ets/database/`：持久化模型与仓库。
- `entry/src/main/cpp/core/`：解析、计算和图像等核心能力。
- `entry/src/main/cpp/utils/`：可复用的原生工具。
- `test/` 与 `entry/src/ohosTest/`：主机侧脚本、场景数据和设备侧测试桥接。

组件应尽量闭环管理局部状态，通过明确的 `@Prop`、回调或数据对象与上层通信。`AppStorage`、`@StorageProp` 等全局状态只用于确实需要跨页面或跨模块共享的设置，不用于省略正常的数据传递。

## 3. 文件与命名

### 3.1 文件命名

- ArkTS 组件、页面、类和主要类型文件使用 `PascalCase.ets`，如 `TopBar.ets`、`EngineService.ets`。
- C++ 类或主要模块文件使用 `PascalCase.h/.cpp`；已有底层入口或解析模块的 `lowercase` 文件名保持不变，新文件跟随所在目录的既有模式。
- PowerShell 脚本使用 `Verb-CalcXSubject.ps1`，共享模块使用 `PascalCase.psm1`。
- 测试文件沿用框架后缀，如 `CalculationCli.test.ets`；场景与用例数据使用小写 kebab-case，如 `navigation-smoke.json`。
- 目录使用小写单词；仅在已有领域目录中扩展，不创建含义重复的新层级。

### 3.2 标识符命名

| 对象 | 风格 | 示例 |
| --- | --- | --- |
| 类、结构体、接口、枚举、类型别名、ArkUI 组件 | `PascalCase` | `EngineService`, `GraphFunctionItem` |
| 函数、方法、局部变量、参数、实例字段 | `lowerCamelCase` | `calculateNative`, `requestId` |
| 模块级常量、协议常量、枚举成员 | `UPPER_SNAKE_CASE` | `MAX_BATCH_ITEMS`, `RESULT_PREFIX` |
| PowerShell 函数 | `ApprovedVerb-CalcXNoun` | `Invoke-CalcXProcessWithTimeout` |
| PowerShell 参数 | `PascalCase` | `$TimeoutSeconds`, `$DeviceId` |
| PowerShell 局部变量 | `lowerCamelCase` | `$resolvedPath`, `$requestJson` |

补充规则：

- 布尔值使用 `is`、`has`、`can`、`should` 等前缀表达条件，如 `isRad`、`hasDMS`。
- 回调使用 `onXxx`，主动执行动作的方法使用动词开头，如 `onHistoryClick`、`validateRequest`。
- 单位应体现在名称中，如 `timeoutSeconds`、`durationMs`，不要依赖调用者猜测。
- 与外部协议、数据库字段或第三方 API 映射时，可保留对方的 `snake_case`；映射完成后的项目内部名称仍使用本项目风格。
- 避免无含义缩写和单字母名称；数学公式中的 `x`、`y`、`t`、循环索引等局部惯例除外。

## 4. 文件头与注释

### 4.1 新文件头

新建 `.ets`、`.cpp`、`.c`、`.h` 文件时，在文件顶部使用以下头注释：

```text
/**
 * Copyright (c) YYYY StartYi. All rights reserved.
 * @file FileName.ext
 * @description 用一句话说明文件当前职责
 * @author StartYi
 * @date YYYY-MM-DD HH:mm
 */
```

- `@description` 描述文件当前承担的职责，不写“新版”“新增”“按要求修改”等过程信息。
- `@date` 记录文件创建时间；普通编辑不反复改写该时间。
- 旧文件头仅在本次修改涉及该头部或内容明显错误时修正，不单独发起全仓替换。

### 4.2 注释写法

- 优先让命名和结构表达“做什么”，注释用于解释“为什么”、边界条件、单位、协议约束或第三方兼容原因。
- 短说明使用 `//`；公开数据契约、非直观算法或有参数/返回约束的接口使用 `/** ... */`。
- ArkTS 文档注释按需使用 `@param`、`@returns`、`@throws`；C++ 公开接口在头文件中使用 `@brief`、`@param`、`@return`。
- 注释应紧邻所描述的代码。代码变化后同步更新注释，过期注释视为缺陷。
- 可以用简短的小节注释区分长函数的阶段，但不要使用大段装饰符号制造视觉噪声。
- `TODO` 必须写明未完成事项和可追踪依据，推荐 `TODO(#123): 说明`；不得用空回调或模糊的 `TODO` 长期占位。
- 除有明确功能开关或兼容原因外，不保留整段被注释掉的旧实现；历史由 Git 保存。

以下注释不应出现在正式代码中：

- 逐句翻译代码行为，如“给变量加一”。
- 协作过程或交付话术，如“新增核心逻辑”“原本逻辑”“按要求保留”“解决你之前的问题”。
- 缺少依据的夸张描述，如“终极方案”“绝对安全”“性能消耗为零”。
- 与当前实现无关的调试日志副本或废弃代码。

## 5. ArkTS 与 ArkUI

### 5.1 格式

- 使用 2 个空格缩进，不使用 Tab。
- 语句以分号结束；字符串默认使用单引号，包含插值时使用模板字符串。
- 左花括号与声明或控制语句同行；`else`、`catch` 与前一个右花括号同行。
- import 按“系统或 Kit、第三方、本地相对模块”分组；组内保持稳定顺序，每条 import 都以分号结束。
- 优先使用 `const`；确实需要重新赋值时才使用 `let`。禁止使用 `var`。
- 导出的函数、公共方法、异步边界和回调写明参数与返回类型；不要用 `any` 绕过类型系统。
- 复杂联合类型、协议对象和跨组件数据优先定义具名 `interface` 或 `type`，避免在调用点重复大型匿名类型。

### 5.2 ArkUI 组件

- `@Component`、`@Entry` 等装饰器紧邻其结构体声明。
- 状态字段、普通字段、回调、私有辅助方法和 `build()` 按稳定分区排列；同类成员放在一起。
- ArkUI 属性链一行一个调用，并保持同一组件内的顺序稳定：尺寸与布局、语义与无障碍、视觉、动画、事件。
- 重复出现的视觉值、按键映射和语义 ID 应抽取为常量或共享配置；仅在单一局部有意义的值保留在组件内。
- 自动化或无障碍需要定位的交互控件，应使用 `SemanticIds` 生成稳定 ID，并提供准确的 `accessibilityText`；不得依赖屏幕坐标或易变的显示文案充当稳定协议。
- 主题相关颜色优先使用 `$r('sys.color...')` 或 `$r('app.color...')`；不要在多个组件中复制同一个硬编码色值。
- 事件处理器较长时提取为具名方法；行内 lambda 只保留简单转发或单一状态更新。

### 5.3 类型、异步与资源生命周期

- 对 JSON、N-API、网络和持久化结果先做类型收窄或结构校验，再访问字段。
- `catch` 中将未知错误收窄为可处理类型，不直接假定存在 `message`。
- 异步函数返回 `Promise<T>`，调用方明确选择 `await`、返回 Promise 或有说明的 fire-and-forget；禁止无意丢弃异常。
- 数据库结果集、计时器、订阅和其他需释放对象应在所有退出路径关闭，必要时使用 `finally`。
- 用户可见文案和需要本地化的文本进入资源文件；协议字面量、数学符号和仅供诊断的稳定标识可保留在代码中。

## 6. C++ 与 N-API

### 6.1 格式与声明

- 使用 4 个空格缩进，不使用 Tab；采用同行左花括号风格。
- 头文件优先使用 `#pragma once`；维护已有 include guard 时，宏名使用大写下划线。
- include 顺序为：对应头文件、C/C++ 标准库、第三方库、项目内头文件；分组之间空一行。
- 类、结构体和枚举使用 `PascalCase`；函数和方法使用 `lowerCamelCase`；新局部变量使用 `lowerCamelCase`。
- 枚举成员和真正的编译期常量使用 `UPPER_SNAKE_CASE`。仅在与 C API、第三方库或现有 ABI 对接时保留其命名。
- 不在头文件中使用 `using namespace`；源文件中的 `using` 也应限制在最小作用域。
- 不依赖隐式窄化转换；跨整数宽度、浮点类型或 N-API 类型转换时使用明确类型并检查返回状态。

### 6.2 边界与资源安全

- N-API 入口先检查参数数量、类型和每一步 API 返回值，再解析业务数据。
- 从 ArkTS 进入 C++ 的模式值、精度、数组长度和字符串长度必须有边界检查；错误应转换为项目约定的错误结果或异常。
- 优先使用 RAII、标准容器和智能指针，避免裸 `new`/`delete` 与手工所有权传递。
- 数学引擎降级路径必须显式区分“可继续尝试的未解析结果”和“必须返回的错误”，不得吞掉未知异常后伪造成功。
- 热路径中的缓存和静态状态要说明键、生命周期及线程假设；不得为了性能牺牲输入隔离或正确性。
- 日志使用项目的 `LOG*` 宏，并避免输出凭据、完整隐私数据或无边界的大型表达式。

## 7. PowerShell 自动化

- 脚本入口使用 `[CmdletBinding()]`，参数块置于文件顶部。
- 使用 4 个空格缩进，并在入口脚本启用 `Set-StrictMode -Version 3.0` 和 `$ErrorActionPreference = 'Stop'`。
- 函数采用 PowerShell 的 `Verb-Noun` 形式，并以 `CalcX` 限定项目域；参数使用 `[Parameter()]` 和具体类型声明。
- 字面量使用单引号；需要变量插值时使用双引号。处理文件路径时优先使用 `Join-Path`、`Resolve-Path -LiteralPath` 和 `Test-Path -LiteralPath`。
- 调用外部进程时显式处理退出码、标准输出、标准错误和超时，不把“进程成功启动”等同于任务成功。
- 供其他脚本消费的标准输出保持机器可读；诊断信息写入标准错误，避免混入 JSON 或协议前缀。
- 返回结构化数据时使用 `[pscustomobject]` 或有序哈希表；不要依赖属性的偶然顺序。
- 临时文件必须在 `finally` 中清理；设备选择、超时和路径解析失败应给出可操作的错误信息。

## 8. JSON、JSON5 与场景数据

- 使用 2 个空格缩进；同一对象中的字段按协议或业务阅读顺序稳定排列。
- 严格 JSON 不写注释和尾逗号；仅 `.json5` 文件使用注释或 JSON5 语法。
- 协议字段、模式值和语义 ID 是兼容性接口，修改时同步更新生产者、消费者、测试和相关文档。
- 测试场景保持最小、可重复；名称描述用户行为或被验证能力，不使用 `test1`、`temp` 等临时命名。
- 模板只提供占位值和配置方法，不包含可用凭据或本机绝对路径。

## 9. 日志、错误与测试代码

- ArkTS 使用项目 `Logger`，C++ 使用 `LOG*` 宏；不要在业务代码中散落临时 `console` 输出或无分类日志。
- 日志说明阶段、对象和结果，避免“进入这里”“看看值”等临时措辞。可恢复错误使用 `warn`，失败使用 `error`，高频路径谨慎使用 `info`。
- 错误消息应说明失败对象和下一步，不暴露秘密，也不把底层异常原样展示给最终用户。
- 测试名称描述行为和期望结果；每个测试聚焦一个行为，准备、执行、断言三个阶段清晰可辨。
- 计算引擎回归优先使用确定性的 LaTeX 输入和结构化结果；UI 场景优先使用语义 ID，不以坐标、动画时序或易变文本作为唯一定位依据。
- 修复缺陷时，应在最接近根因的测试层添加覆盖；如果无法自动化，需在变更说明中记录实际人工验证边界。

## 10. 检查与例外

提交前至少完成与改动相匹配的检查：

1. 查看差异，确认没有无关格式化、调试输出、真实凭据或生成文件。
2. 运行 `git diff --check` 检查空白错误。
3. ArkTS 改动使用 [`code-linter.json5`](../code-linter.json5) 中的 recommended、performance 和 security 规则检查。
4. C++ 改动检查编译器与 DevEco Studio 诊断，并重点关注未使用 include、未使用函数、类型转换和 N-API 返回值。仓库当前未提交统一的 `.clang-format`，不得用个人格式化配置重排无关代码。
5. PowerShell、协议或测试数据改动运行对应的语法检查或最小自测试。
6. 仅当改动涉及构建配置、依赖、公共 API、路由、全局样式或构建输出时，才默认扩大到构建验证；纯文档、注释和局部样式改动不要求构建。

确需违反本文档时，应让例外尽可能局部，并在代码注释或变更说明中记录技术原因。不得通过关闭整类 lint 规则来掩盖单点问题。
