# Windows CLI 调用优化计划

- 状态：待实施
- 类型：开发与测试工具优化
- 编写日期：2026-09-16
- 适用范围：Windows PowerShell、HDC、`entry/ohosTest`

## 1. 背景

当前 Windows 调用器每执行一次计算，都会启动一次 `hdc shell aa test`。测试运行器随后启动 `CalculationTestAbility`、创建测试窗口、加载 `calculator.html`，处理一个请求后结束测试会话。因此，连续执行多条命令时，设备会反复显示测试应用启动和退出。

现有调用方式也偏长：

```powershell
.\test\Invoke-CalcXCalculation.ps1 '1+1'
```

如果通过 PowerShell Profile 定义函数并在函数中写入仓库绝对路径，不同合作者会因克隆目录不同而无法直接复用。

## 2. 目标

本次优化分为两个必须完成的目标和一个条件性目标：

1. 在仓库内提供不依赖本机绝对路径的短命令。
2. 提供批量计算模式，使一批表达式只创建一次 `aa test` 会话并只加载一次测试 WebView。
3. 仅在批量模式仍不能满足实际使用需求时，再评估可跨多次命令调用复用的常驻会话。

预期调用形式：

```powershell
.\calcx.ps1 '1+1'
.\calcx.ps1 'x+1=2' -Mode equation
.\calcx.ps1 -BatchPath .\test\cases\smoke.json
```

## 3. 不在本次范围内的内容

- 不把测试入口加入正式 `entry/default/release` HAP。
- 不修改正式界面、按键映射、历史记录或用户设置。
- 不把正常运行的 `EntryAbility` 改造成命令服务器。
- 不用 CLI 结果替代真实按键与界面测试。
- 不删除现有 `test/Invoke-CalcXCalculation.ps1`，避免破坏已有自动化调用。
- 不在仓库脚本中写入设备 ID、SDK 目录或项目目录的机器专属绝对路径。

## 4. 设计原则

### 4.1 仓库相对定位

在仓库根目录新增 `calcx.ps1`。包装脚本使用 `$PSScriptRoot` 获取自身所在目录，再调用：

```text
test/Invoke-CalcXCalculation.ps1
```

这样仓库无论克隆到哪个磁盘或目录，调用方式都保持一致。包装脚本必须透传参数、标准输出、标准错误和退出码。

不把 PowerShell Profile 函数作为仓库级主要方案。Profile 可以作为个人可选别名，但不能成为其他合作者运行 CLI 的前置条件。

### 4.2 保留单次模式

现有“一次命令、一次请求、一次测试会话”行为继续保留，作为：

- 向后兼容入口；
- 冷启动和生命周期测试入口；
- 进程级状态隔离基线；
- 批量结果的对照基线。

### 4.3 批量模式优先于常驻服务

批量模式在一次 `aa test` 中依次处理多个请求，可复用同一个 WebViewController 和原生计算进程。它能够消除测试套件中绝大部分重复启停，同时不需要引入端口监听、后台服务或长期驻留进程。

批量请求必须保持每条表达式独立的 `requestId`、配置、结果和错误信息，并按输入顺序返回。

### 4.4 默认输出保持兼容

单次模式继续输出一行紧凑 JSON。可增加 `-ResultOnly` 作为人工调用的便捷选项，但自动化默认输出不能丢失以下诊断字段：

- `requestId`
- `inputLatex`
- `normalizedLatex`
- `mathJson`
- `resultLatex`
- `stage` 和 `error`

批量模式建议每个请求输出一行独立 JSON（NDJSON），避免一个超长响应超过测试控制台单行限制。

## 5. 分阶段实施

### 阶段 0：建立当前行为基线

步骤：

1. 记录现有单次命令的成功输出、错误输出和退出码。
2. 记录连续运行多条命令时的 APP 启停次数。
3. 选定 standard、matrix、equation、角度制、指定精度和非法输入基线用例。
4. 保存每个基线用例的 `normalizedLatex`、`mathJson` 和 `resultLatex`，用于后续逐项比较。

验证目标：

- 能明确证明现有模式是一条命令对应一次测试会话。
- 后续优化前后使用完全相同的输入和配置进行比较。
- 不修改正式应用设置和历史记录。

### 阶段 1：增加可移植的短命令

计划文件：

- 新增 `calcx.ps1`。
- 必要时小幅调整 `test/Invoke-CalcXCalculation.ps1` 的参数透传兼容性。

步骤：

1. 使用 `$PSScriptRoot` 解析仓库内调用器路径。
2. 原样透传位置参数和命名参数。
3. 原样转发标准输出、标准错误和 `$LASTEXITCODE`。
4. 保留原调用器作为真实实现，根目录脚本只负责便携入口，不复制协议逻辑。
5. 可选增加 `-ResultOnly`，但默认仍输出完整 JSON。

验证目标：

- 将仓库复制或克隆到不同目录后，`./calcx.ps1 '1+1'` 仍可运行。
- 仓库脚本中不存在 `E:\Projects\CalculatorX` 等本机项目绝对路径。
- 新旧入口对相同参数产生相同 JSON 和退出码。
- `-Mode`、`-Angle`、`-Precision`、`-DeviceId`、`-TimeoutSeconds` 和 `-HdcPath` 均可正常透传。

### 阶段 2：定义向后兼容的批量协议

计划文件：

- 修改 `test/Invoke-CalcXCalculation.ps1`。
- 修改 `entry/src/ohosTest/ets/test/CalculationCli.test.ets`。
- 复用 `entry/src/ohosTest/ets/utils/CalculationTestBridge.ets` 的单条计算逻辑。

步骤：

1. 保留现有协议版本 1 的单请求处理方式。
2. 为批量请求定义独立且可识别的请求信封；若字段不兼容，则提升批量协议版本，不静默改变版本 1 的含义。
3. 每个批量项目包含独立的 LaTeX、模式、角度制、精度和请求 ID。
4. 设备端在同一个 Hypium 用例内顺序调用 `CalculationTestBridge.calculate()`。
5. 每完成一个项目立即输出带请求 ID 的结果标记，不等待整批完成后拼接超长 JSON。
6. 对批次数量、单条长度和总请求长度设置明确上限，并在 Windows 端发送前校验。
7. 一条计算失败时继续处理其余项目，最终退出码表示该批次是否存在失败。

验证目标：

- 协议版本 1 的现有单次命令不受影响。
- 批量结果数量、顺序和请求 ID 与输入完全对应。
- 单条错误不会造成其他结果丢失。
- 特殊字符、Unicode、引号和反斜杠能够完整往返。
- 大批量输入在达到限制前得到明确错误，不发生静默截断。

### 阶段 3：实现批量命令及生命周期优化

计划接口：

```powershell
.\calcx.ps1 -BatchPath .\test\cases\smoke.json
```

后续可在不增加歧义的前提下支持管道输入：

```powershell
Get-Content .\test\expressions.txt | .\calcx.ps1 -Batch
```

步骤：

1. Windows 端一次解析 HDC 路径并选择设备。
2. 将整批请求通过一次 `hdc shell aa test` 发送。
3. 设备端只启动一次 `CalculationTestAbility` 并加载一次 `calculator.html`。
4. 逐条解析响应，输出 NDJSON 或结构化汇总。
5. 提供批次汇总信息，但不污染供程序读取的标准输出。
6. 保留超时、协议错误、设备错误和计算错误的现有分类。

验证目标：

- 一批 N 条表达式只出现一次测试 Ability 启动和一次退出。
- 每条批量结果与独立单次调用的结果一致。
- standard、matrix、equation、角度制和精度配置可在同一批次中混用。
- 批量执行不会写入正式界面历史或修改用户设置。
- 中途出现非法表达式时，其余表达式仍有完整结果。

### 阶段 4：检查同进程状态隔离

复用进程可能暴露单次冷启动测试没有的状态残留，因此必须单独验证。

步骤：

1. 将相同用例按不同顺序批量执行并比较结果。
2. 在可能产生符号、变量或模式状态的表达式之间插入普通算术用例。
3. 比较批量模式、单次模式和真实 UI 的最终 LaTeX。
4. 如果发现状态污染，优先增加明确的每请求重置步骤；无法可靠重置时，不把该类用例放入同一批次。

验证目标：

- 批量结果不依赖前一条表达式或执行顺序。
- 同一输入和配置在单次与批量模式中得到相同 `mathJson` 和 `resultLatex`。
- 无法消除的状态边界被明确记录，而不是隐藏在调用器内部。

### 阶段 5：按条件评估常驻会话

只有满足以下任一条件时才进入该阶段：

- 自动化框架必须在运行过程中动态产生下一条表达式，无法预先组成批次；
- 批量模式的单次启动成本仍明显影响测试效率；
- 人工调试确实需要多次独立输入而不希望测试 Ability 退出。

候选交互形式：

```powershell
.\calcx.ps1 start
.\calcx.ps1 run '1+1'
.\calcx.ps1 run '\frac{1}{2}+\frac{1}{3}'
.\calcx.ps1 stop
```

实施前必须先在设备上验证测试包可用的通信方式、后台生命周期和权限边界，再决定具体传输机制。常驻入口仍须完全位于 `ohosTest`，并具备：

- 会话 ID 和请求 ID；
- 启动状态检查；
- 超时与失联恢复；
- 显式停止和异常清理；
- 并发请求拒绝或排队策略；
- 正式 release HAP 隔离检查。

如果批量模式已经满足速度和易用性要求，则停止在阶段 4，不引入常驻会话。

## 6. 验证矩阵

| 场景 | 单次模式 | 批量模式 | 真实 UI 对照 |
| --- | --- | --- | --- |
| `1+1` | 必测 | 必测 | 必测 |
| 分数 LaTeX | 必测 | 必测 | 抽样 |
| degree 三角函数 | 必测 | 必测 | 抽样 |
| 指定精度 | 必测 | 必测 | 抽样 |
| matrix | 必测 | 必测 | 抽样 |
| equation | 必测 | 必测 | 抽样 |
| 非法表达式 | 必测 | 必测 | 不要求 |
| Unicode 与特殊字符 | 必测 | 必测 | 不要求 |
| 多条混合成功与失败 | 不适用 | 必测 | 不要求 |
| 调换用例顺序 | 不适用 | 必测 | 不要求 |
| 冷启动 | 必测 | 每批一次 | 不要求 |

## 7. 静态与设备验证边界

按当前项目规则，不由 Codex 执行编译或构建。每一阶段先完成以下非编译检查：

1. PowerShell AST 语法检查。
2. Windows 协议 `-SelfTest`。
3. 参数校验、Base64、JSON 和退出码的本地测试。
4. 旧入口兼容性与绝对路径扫描。
5. `git diff --check` 和文档链接检查。

需要新测试 HAP 的设备验证由维护者完成构建和安装后再继续，包括：

- 单次与批量计算结果对照；
- APP 启停次数观察；
- 状态隔离验证；
- 测试 HAP 使用真实 `libentry.so` 的检查；
- 正式 release HAP 不含测试入口的隔离检查。

## 8. 完成标准

满足以下条件后，CLI 优化可视为完成：

- 合作者无需修改脚本即可从任意克隆路径执行 `./calcx.ps1`。
- 仓库内没有机器专属的项目绝对路径。
- 原有 `Invoke-CalcXCalculation.ps1` 调用保持兼容。
- 批量模式在一次 `aa test` 会话中完成多条计算。
- 批量与单次结果逐项一致，且失败项可独立定位。
- 已验证或明确限制同进程状态隔离问题。
- 正式 APP 的界面、设置、历史记录和 release 包均不受影响。
- 正式操作文档和变更说明与最终实现同步更新。
