# 基础计算键盘沉浸光感试点计划

- 状态：实现完成，主包 debug 构建通过，待 API 26 真机验证
- 最近验证：2026-09-21，`entry/default/debug assembleHap` 构建成功
- 编写日期：2026-09-21
- 适用分支：`feature/api-26-sensation`
- 目标 API：`26.0.0`
- 最低兼容 API：`6.1.0(23)`，保持不变
- 试点范围：仅基础计算模块 `BasicCalc`
- 核心策略：先建立可回退的结构检查点，再验证原生材质；原生路线不可行时再评估高保真自研效果

## 1. 目标与信心边界

本计划用于验证基础计算键盘能否在不破坏现有布局、计算、触感和低版本兼容性的前提下，为每一个可见按键提供接近系统原生品质的沉浸光感。

本试点对最终视觉目标有信心，但不预先假定实现一定来自同一种技术：

1. 首选目标是真正的 ArkUI API 26 `uiMaterial.ImmersiveMaterial`；
2. 如果官方支持区域无法合理承载多行计算键盘，则评估由 ArkUI 视效组合实现的高保真自研效果；
3. 最终文档必须准确说明采用的是系统材质还是自研视效，不把自定义模糊描述为系统沉浸光感。

试点成功后再决定是否抽象成全局键盘能力，以及是否扩展到科学、方程、矩阵、汇率和图形键盘。本阶段不提前重构其他模块。

## 2. 成功定义

只有同时满足以下条件，基础键盘试点才算成功：

- 19 个可见按键均具有稳定、清楚的材质层次；
- 数字、运算符、删除/清空和等号仍保留明确的语义区分；
- 点按时的光源、形变或高光反馈自然，没有与旧缩放、透明度和阴影叠加成双重动效；
- 深色、浅色和系统可用的不同沉浸光感档位下均保持文字与图标可读；
- `=` 纵跨两行、空占位、网格间距、键盘圆角和底部安全区与当前布局一致；
- 退格单击和长按连续删除保持当前行为；
- 触感反馈、Semantic ID、可访问性文本和 `screen_handle_action` 事件保持不变；
- API 23 路径完整保留当前背景、边框、阴影和按压反馈；
- API 26 上没有明显点击延迟、掉帧、异常发热或持续高 GPU 占用；
- 失败实验可以只回退对应提交，不影响已经验收的结构整理。

## 3. 当前实现基线

### 3.1 页面结构

`BasicCalc.ets` 当前是一个全高 `Column`：

```text
BasicCalc
├─ FormulaScreen：45%
└─ Keyboard container：55%
   └─ Grid：5 行 × 4 列
      └─ BasicKeyItem × 19
```

键盘容器使用主背景、40vp 顶层圆角、向上的阴影和底部导航区域内边距。按键使用圆角、语义背景色、顶部/左侧高光边框、阴影、缩放点击效果与 pressed/normal 状态样式。

### 3.2 不能回归的交互

- `BasicKeyItem` 保留当前 Semantic ID 与可访问性文本；
- 所有按键继续通过 `handleKeyPress()` 触发触感反馈和 `screen_handle_action`；
- 退格按下 500ms 后以 80ms 间隔连续触发，手指抬起或取消时停止；
- `=` 继续占据第 4、5 行的同一列；
- 基础计算继续使用 `FormulaScreen({ moduleType: 'basic' })`；
- 公式区与键盘的 45%/55% 关系，以及全屏与小窗下的现有表现，必须先作为基线保留。

### 3.3 已知平台边界

当前应用已经满足以下前提：

- `targetSdkVersion` 为 `26.0.0`；
- `compatibleSdkVersion` 为 `6.1.0(23)`；
- entry module 的 `ohos.arkui.UIMaterial.state` 为 `default`；
- `ImmersiveMaterialUtils.ets` 已有 Sheet、弹窗、菜单、搜索框和 TopBar 的材质工厂；
- TopBar 已使用直接、正向的 `deviceInfo.apiAvailable('26.0.0')` 分支保护 API 26 调用。

官方当前限制是：弹窗类组件和少量选择类组件可以在页面任意区域生效；其他普通组件只在 `Navigation`/`NavDestination` 标题栏，或横向 `Tabs` 中 `barPosition = BarPosition.End` 的底部 TabBar 内生效。

历史分支曾直接给普通内容区中的 `BasicKeyItem` 设置交互式 `ULTRA_THIN` 材质。该实现没有解决生效区域问题，最终未进入 `main`。本试点不得重复只加 `systemMaterial`、不改变组件区域的方案。

## 4. 待验证假设

### H1：单 Tab 的自定义底部 TabBar 可以承载完整键盘

首选原生结构是让公式区成为唯一的 `TabContent`，并把现有键盘 `Grid` 作为该 Tab 的自定义底部 TabBar Builder：

```text
Tabs(barPosition: End)
└─ TabContent
   ├─ content: FormulaScreen
   └─ custom tabBar: BasicKeyboard Grid
```

该结构的预期优势：

- 页面只有一个 Tab，不需要把 19 个按键错误建模成 19 个页面；
- 键盘整体进入官方声明的底部 TabBar 生效区域；
- 原有 `Grid`、跨行等号、事件回调和语义 ID 可以继续保留；
- 公式区和键盘仍由同一个 `BasicCalc` 管理；
- 若材质实验失败，可以回退 Tab 容器提交，恢复当前 45%/55% `Column`。

必须通过真机回答以下问题：

1. 自定义 TabBar Builder 的后代 `Button` 是否被系统识别为有效材质区域；
2. 单 Tab 的自定义 Builder 是否会引入选中态、点击拦截或页面切换行为；
3. TabBar 高度能否稳定匹配现有 55% 键盘区域，并响应窗口尺寸变化；
4. 多行 `Grid` 是否会被 TabBar 自身的裁剪、默认内边距或手势处理影响；
5. 可访问性是否仍把内部控件识别为按钮，而不是错误合并成单个页签；
6. TabBar 与底部导航安全区是否会重复避让；
7. `systemMaterial` 的交互光源是否在所有按键上正常跟随触点。

任一关键问题无法稳定解决时，停止扩大该结构，不使用多层嵌套 Tabs、负边距或不可解释的坐标偏移绕过限制。

### H2：半模态容器可以为整个键盘坞提供原生材质

如果 H1 无法提供逐键材质，可用 `bindSheet` 做第二个原生方向的短实验：

- 使用固定高度或 detent 保持键盘区域尺寸；
- 使用 `enableOutsideInteractive` 保留公式区交互；
- 使用透明遮罩、隐藏拖拽条和关闭入口；
- 为 Sheet 表面设置系统材质。

该方案只能直接证明“整个键盘坞”可以使用原生材质，不能自动证明 Sheet 内部的每个普通按钮都能使用系统材质。如果只能得到整块面板材质，将它作为独立设计候选，不把它描述为逐键沉浸光感。

### H3：自研视效可以达到可接受的原生观感

只有 H1、H2 都不能满足目标时才进入此路线。自研效果需要拆解并分别实现：

- 透光与背景模糊；
- 边缘高光与内外阴影；
- 轻量折射或亮度变化；
- 随触点移动的局部高光；
- 按下时的非线性缩放和回弹；
- 深浅色与语义色自适应；
- 低性能设备的降级策略。

自研路线不得复制系统私有资源，不宣称拥有系统材质的算力自适应能力。最终是否可接受，以与系统组件和参考产品的并排真机录屏为准。


## 7. 验证矩阵

### 7.1 静态与构建

- `git diff --check`
- Markdown 相对链接与结尾换行检查
- API 26 调用全部位于直接、正向的 `deviceInfo.apiAvailable('26.0.0')` 分支
- `systemMaterial` 与 `backgroundColor`、border、shadow 的属性顺序检查
- 主包 debug 构建
- 最终收敛后按风险决定是否补充 ohosTest debug 与 release 构建

构建只证明代码可以编译，不证明系统材质生效、API 23 可运行或真机性能合格。

### 7.2 视觉

| 维度 | 最低覆盖 |
| --- | --- |
| 系统版本 | API 26；最终方案补 API 23 |
| 主题 | 浅色、深色 |
| 沉浸光感设置 | 测试设备可用的关闭、低、中、高或等价档位 |
| 设备形态 | 手机竖屏；再补横屏、小窗和平板 |
| 按键分类 | 数字、运算符、AC、退格、等号、百分号 |
| 状态 | normal、pressed、连续点击、长按退格 |
| 布局 | 普通窗口、受限高度、底部导航区域变化 |

检查：

- 文字和图标对比度；
- 材质透光层次；
- 边缘高光是否完整；
- 圆角和阴影是否被 Grid 或 TabBar 裁剪；
- 触点光源是否准确；
- 等号跨行区域是否发生拉伸异常；
- 系统材质关闭或降级时是否仍能辨认按键边界。

### 7.3 交互与行为

- 所有 19 个按键产生正确 action；
- 退格单击一次只删除一次；
- 长按退格在 500ms 后开始连续删除，并在 Up/Cancel 后停止；
- 触感反馈开关和强度保持有效；
- FormulaScreen 输入、计算、历史入口与清空行为无变化；
- Semantic ID 与可访问性文本保持稳定；
- 单 Tab 不发生无意义页面切换；
- 公式区在键盘显示时仍可点击和滚动；
- 返回键、模块切换、前后台切换和旋转后状态正常。

### 7.4 性能

- 快速连续点击 30 秒；
- 长按退格连续触发；
- 深浅色切换后连续操作；
- 记录主观触摸延迟、掉帧、温度变化；
- 条件允许时使用 ArkUI Inspector、AppAnalyzer 或 Profiler Frame 对比基线；
- 避免为 19 个按键每次重建相同材质对象；
- 如果性能不合格，先减少交互光效和重复渲染，再决定是否放弃路线。

## 8. Git 检查点与精确回退

提交应遵循“每个提交只有一个可验证目的”：

| 检查点 | 内容 | 可独立保留 |
| --- | --- | --- |
| C0 | 试点计划 | 是 |
| C1 | 无视觉变化的基础按键视觉层拆分 | 是 |
| C2 | 单 Tab 自定义底部 TabBar 原型 | 仅验证通过后 |
| C3 | 逐键原生材质收敛 | 依赖 C2 |
| C2B | Sheet 键盘坞原型 | 与 C2 二选一 |
| C3B | 自研光感表面与交互动效 | 从 C1 开始 |
| C4 | 最终文档与扩展决策 | 是 |

回退规则：

- 结构实验失败：只回退 C2/C2B，保留 C1；
- 材质视觉失败：回退 C3，保留已经验证的容器结构前提是该结构本身仍有价值；
- 自研效果性能失败：按视效层逐个回退，不影响基础按键行为；
- 提交已经共享后不重写公共历史，使用新的 Conventional Commit 撤销对应差异；
- 不使用会覆盖用户其他改动的整棵工作树重置；
- 每次提交前检查 `git status`、暂存文件列表和实际 diff，不使用 `git add -A`。

## 9. 停止条件

出现以下任一情况时停止当前路线并回到最近稳定检查点：

- 真机确认材质不在目标区域生效；
- 必须使用多个嵌套 Tabs、负边距或屏幕坐标硬编码才能维持布局；
- 内部按键被可访问性错误合并成 Tab；
- 公式区或按键出现点击拦截；
- 退格连续触发、触感反馈或计算事件发生回归；
- API 23 出现透明按钮、崩溃或兼容告警；
- 语义颜色明显丢失；
- 快速点击出现可感知延迟、掉帧或发热；
- 关闭沉浸光感后按键边界不可辨认；
- 为试点引入了其他键盘或计算引擎改动。

## 10. 完成标准

- 基础键盘最终采用的技术路线已经由 API 26 真机证据确认；
- 逐键或整块键盘坞的实现范围被准确描述；
- 所有基础按键视觉、计算、连续退格、触感、语义 ID 和布局通过验收；
- API 23 保持当前视觉和行为；
- 性能结果足以支持继续试点，或已明确记录停止原因；
- Git 历史中计划、结构、实验、收敛和文档各自可独立回退；
- 失败路线没有遗留无效代码、设置入口或偏好项；
- 只有基础试点完成后，才形成其他键盘的后续迁移计划。

## 11. 本计划不包含

- 当前阶段不修改任何 ArkTS、JSON5、资源或测试代码；
- 不在计划提交中执行构建、安装或真机测试；
- 不提前添加“键盘沉浸光感”设置开关；
- 不同时重构其他五类键盘；
- 不修改 `KeyGestureWrapper` 的手势状态机；
- 不改变基础计算布局、按键数量或计算语义；
- 不在缺少真机证据时宣称已经达到系统原生效果；
- 不提交、推送、合并或发布实现代码，除非当前阶段获得相应授权。
